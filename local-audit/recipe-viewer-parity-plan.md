# Recipe-viewer parity plan

Reviewed September 28, 2026. The audit and matrix below describe the pinned baseline. A first implementation now follows at the end of this document; its narrower coverage must not be mistaken for full parity. No graphical client or pack change was made for this work.

The smallest faithful route for the selected pack is to retain BMC6's REI, move synchronized recipe access out of the JEI plugin, restore official display semantics once, and supply optional JEI 29 and REI adapters over those semantics. Start with a useful subset, but keep all fifteen official custom categories and the additional vanilla-category behaviors as explicit completion requirements. Installing JEI alone would not restore the three missing categories or newer display interfaces; replacing REI would also require testing the other pack integrations.

Fifteen categories are the minimum category inventory. Vanilla crafting, smelting and fueling integration below adds behavior without adding more custom Tinkers categories. Do not count a category as complete merely because its title is registered or one sample recipe appears.

## Gaps inside and beyond the three new categories

**Fuel.** Existing `MeltingFuel` already supplies `getInputs`, `getDuration`, `getTemperature`, `getRate` and fluid-dependent `getAmount`. This is the smallest missing-category slice. Current `MeltingFuelHandler.SOLID_FUELS` is a memoized list of coal, charcoal, oak log, oak planks and blaze rod. Official enumerates actual fuel items and caches burn times, with a fuel-examples tag for illustrative rotation. Target mechanics already use `level.fuelValues().burnDuration(stack)` and `EventHooks.getItemBurnTime(stack, burnTime, TinkerRecipeTypes.FUEL.get(), level.fuelValues())` in `SolidFuelModule`/`HeaterItemHandler`. Reuse those target rules instead of claiming the five examples are exhaustive. Compare actual heater duration conversion before copying old widget divisors. A fuel page must report resource cost and temperature accurately; it must not alter the recipes or introduce new fuel efficiencies.

**Materials.** Official adds `IDisplayMaterialRecipe` to both `MaterialRecipe` and `MaterialFluidRecipe`; its contract covers recipe ID, `MaterialVariant`, display items/value/leftover, fluids, and optional composite input material. Continuum has useful underlying data but lacks that interface and the Material ingredient type. Its caches expose `MaterialRecipeCache.getAllRecipes`, `MaterialCastingLookup.getAllCastingFluids` and `getAllCompositeFluids`, while official uses sorted forms. Adapt those existing caches with deterministic material/recipe ordering. Do not turn a material into a fake craftable item just to make the browser index it.

**Tool tinkering.** Official adds `IDisplayTinkerStationRecipe`, `IDisplayToolTinkering`, `IDisplayCraftingTinkering`, `FilteredRecipe`, `FilteredItemRecipe`, `FilteredFluidRecipe` and `VanillaFilteredRecipe`. `IDisplayToolTinkering` distinguishes tool catalysts from consumed/replaced tools and supplies a title/tooltip. Producers include material swapping, fixed/tool material swapping, material value/index swapping, part-swapping overrides and repair recipe expansions. Some of these newer gameplay recipes are themselves missing from the port. Viewer work must show only implemented server recipes, and retain the missing gameplay recipes in the port's separate parity queue. A page suggesting an unavailable recipe is not fidelity.

The parallel armor/material workstream is now implementing `MaterialIndexSwappingRecipe`, `MaterialValueSwappingRecipe`, their builder/registration and traveler armor recipes. Those changes are in progress, not accepted parity evidence in this plan. Once accepted, include their actual input count, chosen material/index, changed tool component and leftover behavior in Tool Tinkering displays. Reuse the tested consumption semantics; an old display implementation must not imply costs different from the server.

**Melting/focused casting.** Official changes the melting category parameter from `MeltingRecipe` to `IDisplayableMeltingRecipe`; `DisplayMeltingRecipe` and material melting can expose input-linked outputs, foundry byproducts and dynamic time without being a concrete normal recipe. Official casting adds `CastingRecipeManager`; generic managers include `SimpleItemRecipeManager`, item/fluid caches and recipe-slot wrappers. These prevent eagerly enumerating every possible material/tool variant and make recipe/use searches sensitive to the focused item/fluid. Port that behavior as bounded, reload-aware display expansion, not a complete Cartesian product of materials, parts and modifiers.

**Vanilla crafting extensions.** Official registers five extension families: `ShapedMaterialRecipe`, `ShapedMaterialsRecipe`, `ShapelessMaterialsRecipe`, `OverslimeCraftingTableRecipe`, and `IDisplayCraftingTinkering`. Current `registerVanillaCategoryExtensions` registers only the first, although some other extension classes exist. Official also copies applicable station repair displays into crafting and uses a focused crafting manager. These are separate requirements from the fifteen-category matrix.

**Ingredients, subtypes and navigation.** Official has four custom ingredient types: ModifierEntry, Pattern, SlotCount, and MaterialVariant. Current code has the first three; their registered collections are empty. Official optionally populates modifiers and registers slot counts. Preserve stable codecs, modifier levels, material variant IDs, item components, fluid/potion contents, retextured workstation variants, bookmarks and hidden-entry behavior. Inspect current codec round trips: for example the current modifier codec reconstructs level 1 from an ID, which cannot preserve arbitrary ModifierEntry levels. Material identity must be distinct from its localized title or rendering icon.

Official runtime registration also honors tool/part material visibility settings, adds configured table/smeltery/anvil and filled-container variants, removes absent compatibility fluids and untyped potion fluid, adds configured potion variants, hides its named easter-egg crafting recipes, and removes crystal/creative-slot items represented by custom ingredients. The current plugin has no `onRuntimeAvailable` implementation. Carry these existing configuration and visibility rules into both adapters rather than treating category registration as the whole integration.

**Catalysts, tank hover and transfer.** Official links retextured workstations, scorched casting blocks, entity melting/fuel, modifier catalysts and qualifying modifiable tools. Current links are fewer and largely default stacks. Official registers tank GUI handlers for melter, alloyer, heating structure and tool container screens; the port contains helper code but does not register `registerGuiHandlers`. Official registers station transfer for both modifiers and tool building; the port currently registers only tool building, plus crafting-station and tool-inventory crafting. Existing `TinkerStationTransferInfo` can provide a starting point for the missing modifier transfer once its custom ingredient roles are checked.

## Synchronization and identity first

The server already requests fourteen custom recipe types through `TinkerRecipeTypes.sendRecipesToClient(OnDatapackSyncEvent)`, registered by `TinkerCommons`: part builder, material, station, worktable, basin/table casting, basin/table molding, melting, entity melting, fuel, alloying, severing and `DATA`. Do not add an independent recipe network or require REI on the dedicated server merely to deliver the same recipes.

`TinkerClient` always queues `RecipeCacheInvalidator.reload(true)`, but retains the received `RecipeMap` and rebuilds the material/casting caches only through a reflective `TConstructJEIPlugin.onRecipesReceived` callback when `jei` is installed. That plugin owns a static map and may use the integrated server as fallback. No map reset was found in the inspected plugin. `TinkerRecipeCacheRebuilder` also falls back to the current server for absent material-fluid `DATA` recipes. An integrated-server success could therefore conceal missing data on a remote client.

Use a small viewer-neutral client recipe holder/listener, retaining the server's `RecipeMap` and registry access independent of either viewer. Coordinate existing `RecipesReceivedEvent`, `MaterialsLoadedEvent` and station-layout updates; rebuild only after the matching synced material/stat/trait/layout data is ready. Clear references and derived displays on logout, replace rather than append on reload, and cover joining a different server in the same client process. Reuse existing invalidation/rebuild methods rather than inventing a second recipe manager. Each viewer reads the current snapshot in its own reload lifecycle; late viewer initialization must also see it.

Core's `RecipeHelper.getJEIRecipes(RegistryAccess, Stream<RecipeHolder<?>>, Class<C>)` has no JEI imports and expands `IMultiRecipe` before filtering, so it is reusable. It catches expansion errors and omits failed recipes; retain diagnostics and assert expected display counts in fixtures so failures cannot silently pass as parity. Keep parent `RecipeHolder.id().identifier()` with expanded display results. `LoadableRecipeSerializer` supplies `mantle:loadable_recipe` as a legacy object-ID fallback and encodes an object's reflective `getId`/`id` separately from the holder. A viewer must not collapse every fallback-ID recipe into one display. Use canonical holder IDs plus stable expansion keys, and test those IDs through JSON decode, network round trip, reload and bookmarks. This is an audit concern, not proof that every current recipe ID is wrong.

## Exact target adapter APIs

For JEI `29.34.0.90`, retain optional `@JeiPlugin` / `IModPlugin`. `IRecipeCategory<T>` uses `IRecipeType<T>`, `setRecipe(IRecipeLayoutBuilder,T,IFocusGroup)`, `getWidth/getHeight`, `GuiGraphicsExtractor` for drawing, `createRecipeExtras`, `getIdentifier` and a category codec hook. `IModIngredientRegistration.register` requires a `Codec<V>` in addition to type, values, helper and renderer. `IAdvancedRegistration.addSimpleRecipeManagerPlugin(IRecipeType<T>, ISimpleRecipeManagerPlugin<T>)` is available; the old `addTypedRecipeManagerPlugin` remains a default bridge. `ISimpleRecipeManagerPlugin` exposes input/output acceptance, recipe lookups and all recipes. These are the target points for official focus managers. Port old `ResourceLocation`, Forge fluid APIs and old GUI drawing calls to the actual 26.1.2 equivalents; do not copy upstream imports unchanged.

For REI `26.1.819`, the JAR exposes:

| Responsibility | Actual target API |
| --- | --- |
| Optional discovery | `@me.shedaniel.rei.forge.REIPluginClient` + `REIClientPlugin`; `@REIPluginCommon` + `REICommonPlugin` for common entry/serializer registration |
| Categories/workstations | `registerCategories(CategoryRegistry)`; `CategoryIdentifier`, `DisplayCategory`, `setupDisplay(Display, Rectangle)`, `CategoryRegistry.addWorkstations` |
| Displays | `registerDisplays(DisplayRegistry)`; `Display`/`BasicDisplay`, input/output/required entry lists, category, location and serializer |
| Display serialization | `Display.getSerializer()` is required; `DisplaySerializer.of(MapCodec, StreamCodec)` and `REICommonPlugin.registerDisplaySerializer(DisplaySerializerRegistry)` |
| Recipe fillers | `DisplayConsumer.RecipeDisplayConsumer.beginRecipeFiller(Class<T extends net.minecraft.world.item.crafting.display.RecipeDisplay>)`; this is **not** the old Recipe-subclass filler API |
| Focused expansion | `DisplayRegistry.registerDisplayGenerator(CategoryIdentifier, DynamicDisplayGenerator)`; `getRecipeFor`, `getUsageFor`, `generate(ViewSearchBuilder)` |
| Custom values | `REICommonPlugin.registerEntryTypes`; `EntryDefinition`, `EntryType`, `EntrySerializer` with `Codec` and `StreamCodec`; client entry renderer registration |
| Subtype comparison | `registerItemComparators` / `registerFluidComparators`; `ItemComparatorRegistry.registerComponents(Item...)` compares all components. Use an `EntryComparator` for deliberate material/tool subtype semantics instead of making all irrelevant component changes distinct |
| Screens | `registerScreens`, `registerFocusedStack`, container click areas, `registerExclusionZones`; cover tank hover and the station side panel |
| Transfer | `registerTransferHandlers`; `SimpleTransferHandler.getInputSlots/getInventorySlots`, `getInputsIndexed`, `SlotAccessor.fromSlot`; server support and permission behavior must be verified |

Construct REI displays from the already-synced custom `RecipeMap`; those recipes do not automatically become vanilla `RecipeDisplay` objects merely by registering a filler. Give each display a real codec/stream codec or another supported serialization strategy verified against this API. Isolate all REI imports/discovery in the optional adapter, including common serializers, so a dedicated server or client without REI does not load its classes. Do not make JEI a dependency of the REI adapter. Reuse domain data and resource identifiers; layout/rendering code remains viewer-specific.

## Implementation order and cost

Costs below describe scope and coupling, not a time estimate or an implementation promise.

| Step | Deliverable | Relative cost and completion boundary |
| --- | --- | --- |
| 1 | Viewer-neutral received-map ownership, reload/logout lifecycle and stable display IDs | Medium; touches recipe/cache lifecycle, with remote-client data ordering as the main risk |
| 2 | Shared display contracts and faithful Fuel/Materials/Tool Tinkering producers; restore JEI extensions/focus behavior | Fuel small; Materials medium; Tool Tinkering/focused variants large because display and missing gameplay producers must be reconciled |
| 3 | REI foundation, codecs, four custom entry types and subtype rules | Medium; target API changed enough that old REI examples cannot be assumed correct |
| 4 | First usable REI slice: table/basin casting, melting/foundry/alloy, part builder | Medium; six categories. This is explicitly partial coverage, not release parity |
| 5 | Remaining nine custom categories, five vanilla extension families, catalysts, GUI lookup and focused generation | Large; completes the category inventory while preserving resource and modifier semantics |
| 6 | Crafting-station, tool-inventory and station transfer for supported recipes | Medium/high risk; use actual slots and server validation after conservation checks, then user-operated remote-client acceptance |

The first useful slice must already preserve costs: quantities, material unit values, consumed versus reusable casts/patterns, leftovers, modifier slot/level requirements, station part order, temperature/time and foundry byproducts. Text-only “see book” placeholders are not replacements for missing categories. No recipe, balance number or actual server behavior should change solely to simplify display code.

For crafting-station transfer, grid slots are `0..8`, result is `9`, adjacent storage occupies `10..(totalSize-36-1)` and player inventory is the final 36 slots; current JEI code filters side inventory slots by `allowModification`. For tool stations use `getInputSlots()` and the real layout rather than fixed offsets. Exclude outputs and decorative modifier/material entries from transfer requirements. The recent shift-click fixes are prerequisites, not proof that either viewer's network transfer is correct. Test partial capacity, leftovers, component-sensitive inputs, restricted side storage, invalid layout, and a server without viewer transfer support before enabling each transfer path.

## Acceptance evidence required

Headless checks can establish recipe codec/network round trips for all fourteen custom types; canonical and expanded display-ID uniqueness; fifteen category mappings; material/slot/modifier codec identity; material/part/tool expansion results; exact quantity/cost fields; empty-tag and failed-expansion diagnostics; focused input/output results; cache replacement across reload; and no optional-viewer class loading on a dedicated server. Fixture expected counts must come from pinned recipe inputs, not guessed totals from a running pack. Include missing newer gameplay recipes as unresolved parity entries rather than fabricating displays.

Separate user-operated client checks are still required with the real BMC6 client connected to the dedicated server: all fifteen categories; crafting/smelting/fueling links; recipe/use searches on tools, parts, materials, fluids and modifiers; focused dynamic results; bookmark round trips; retextured workstations; tooltips, fluid units and cycling variants; tank hover; side-panel overlap; keyboard focus; initial loading and reload/empty/error states; reconnect to a different server; and transfers under partial/full inventories. Compare JEI and REI against the same synced data when testing JEI separately. No simultaneous-viewer recommendation or pack browser replacement is made here.

## First implementation checkpoint

The first source implementation adds optional `plugin/rei/` adapters, with six categories: casting basin, casting table, melting, foundry, alloying and fuel. It does not change the selected pack or enable REI in development runs. Existing JEI category registration remains in place.

`ClientRecipeCache` now owns the received map and a revision independently of either viewer. `TinkerClient` receives recipes without a JEI-presence check, refreshes after material events and clears on logout. JEI reads the same snapshot instead of its own static map or an integrated-server fallback. The new `TinkerRecipeCacheRebuilder.rebuildClient`/`MaterialCastingLookup.rebuildRecipesExact` path replaces material fluid data even when DATA is empty; the existing server fallback path is unchanged. `ClientRecipeCacheTest` exercises the actual recipe maps and material casting cache for replacement, late material refresh, empty DATA, second-server data and logout. It does not require either viewer on the test runtime.

REI uses category-scoped `DynamicDisplayGenerator`s. Inspection of the installed `ViewsImpl.generateLiveDisplays` confirms those generators run independently of static displays, including category-only searches; the generator's general `generate` method deliberately returns nothing for focused searches, whose results come from `getRecipeFor`/`getUsageFor`. The generated cache is rebuilt when the received-map revision changes. This avoids issuing an unverified global REI reload from packet handlers.

Each `SmelteryDisplay` has a real `MapCodec` and registry-aware stream codec registered through an optional REI common plugin. Display identity combines the canonical recipe-holder ID with a SHA-256 of canonical serialized content, preserving component and quantity differences without depending on expansion order or a legacy recipe object's fallback ID. Casting expands paired cast/output variants separately. The standard slot layout separates consumed inputs, outputs and reusable casts/alloy catalysts. Melter/smeltery ore quantities remain distinct, and foundry outputs use the recipe's byproduct logic. Fluid components survive the NeoForge-to-Architectury conversion. Material-part comparators retain material identity while ignoring unrelated damage/name components; potion-fluid comparisons include components.

Fuel pages enumerate registered default item stacks through the same target fuel-values/hook rule as `SolidFuelModule`, show solid-fuel crafting remainders restored by the parallel heater fix, and show liquid fuel quantities, temperature, duration and speed. Burn time is labeled for minimum fuel consumption because larger controllers can spend fuel faster. Melting time is labeled as base time because fuel rate changes it. These displays do not provide transfer buttons.
